双Map统计接口调用量

2025-07-01

一、系统核心设计目的

目的是在 高并发接口调用环境（TPS>10w） 下，实时统计各调用方（Code）对每个接口的调用次数，并定期将统计数据上报到消息队列 MQ。

二、为什么需要使用“双 Map”？

背景场景：调用量统计系统

  • 每次接口调用都要统计次数（实时、频繁）
  • 统计数据要定期上报（如每 10 秒、每分钟发送一次到 MQ）

这两个动作：

动作 特点
实时统计（update） 高频、写操作、多线程并发写入
定期上报（report） 批量读、读完后还要清空数据

这两个动作会同时进行，而写入和清空之间可能冲突，这就是引入双 Map 的根本原因。

三、如果只使用一个 Map，会遇到的问题

场景1：写入过程中被清空，导致数据丢失

copy// 线程 A：接口调用，update 还没完成
map.put(key, value);

// 线程 B：定时任务开始 report，清空 map
map.clear();  // 刚好线程 A 的写入被覆盖或丢失

场景2：定时任务统计的数据可能不完整

  • 比如你每 10 秒上报一次 map 中的调用量
  • 在第 9 秒，有用户请求正在更新 map，此时定时器开始读取和清空 map
  • 这个“正在进行的请求”的数据，可能：
    • 被读到一半（数据不一致）
    • 被清空还没写完（丢失）

场景3：map.size() 还没变，但内容已经变了（读到脏数据）

四、使用“双 Map”的好处

核心思想：写读分离，互不干扰

  • 两个 Map：mapA, mapB

  • activeMap：当前写入使用的 Map

  • 每次定时任务

    report()

    时：

    • 切换 activeMap 指针：从 A → B（或 B → A）
    • 新的请求都写入新的 Map（例如 B）
    • 定时任务可以安心地读取并清空旧的 Map（A）

效果：

优点 说明
数据一致 report 期间不再写入旧 Map，避免数据丢失或读到脏数据
线程安全 没有必要加锁，也不会影响写入线程
性能更高 写线程和读线程互不干扰，系统吞吐量提升明显

五、为什么定时上报之后还必须清空统计数据？

一、系统设计目标回顾

设计的是一个调用量统计系统，目标是：

实时记录各调用方对各接口的调用次数，并定时上报到 MQ 或日志系统进行存储/分析/展示。

而这个“调用次数”其实是一个时间段内的增量数据（例如过去10秒的调用量），并不是一个永久累计值。

二、为什么上报后必须清空数据？

1. 避免重复上报

  • 如果不上报后清空数据，Map 中的计数会一直累加。
  • 下一次上报时，仍然是累计总数。
  • 那每次上报的都是重复的数据，监控图表/日志分析就会错误。

比如：

时间点 实际调用数 累计值（如果不清空） 上报值
第10秒 100次 100 100
第20秒 50次 150 ❌150（应该是50）
第30秒 30次 180 ❌180（应该是30）

2. 节省内存空间

  • 每次调用都在向 Map 中写入数据。
  • 如果不清空 Map，数据会无限增长，最终导致：
问题 后果
内存泄漏 系统内存越来越大，GC 压力加剧，甚至 OOM
冗余数据 Map 中可能保留了早就没用的接口/调用方数据

清空后，Map 是“干净”的，下一轮统计可以轻松开始。

3. 符合“时间窗口统计”的设计理念

  • 统计系统实际上在模拟一个“滑动窗口”或“时间窗口”的统计逻辑。
  • 每次上报的是过去 X 秒的数据（比如 10 秒）。
  • 如果不清空，数据就会跨窗口重叠，破坏统计精度。

三、如果不清空会发生什么问题？

问题类型 描述 后果
数据重复 每次上报的数据包含上次的内容 上层系统误以为调用量持续暴涨
内存积压 Map 数据不断累积 内存使用量增长，GC频繁甚至OOM
统计错误 指标不再代表过去 10 秒，而是整个生命周期 图表变成斜线，不再有波动性
流量预测不准 会把过去所有历史调用算进来 告警、限流等都会被误触发

四、有没有不清空的情况？

有，但前提是设计的不是“增量上报”，而是“全量状态上报”。比如：

  • 是一个长期总调用次数的记录系统（如累加 PV）
  • 每次上报前后都保存上一次的快照，取“当前值 - 上次值”作为增量

这种方式需要更复杂的状态管理，远不如清空来得直接、简洁、可靠。

update()方法实现细节

首先有一个业务背景，接口的调用量是很大的，所以update()方法的并发量是很高的，而report()方法的调用量就比较低，仅仅被内部的ScheuleExecutorService定时任务线程池调用，每隔一定的时间上报到MQ中，所以这就要求update()方法具有很高的性能。而基本实现有三种方式，分别为synchronized + HashMap、 ConcurrentHashMap + get+put、ConcurrentHashMap + merge()。

调研结论

操作方式 吞吐 TPS 延迟
synchronized + HashMap 低（<3w） 高
ConcurrentHashMap + get+put 中等（5w~6w） 中
ConcurrentHashMap + merge() 高（>10w） 低

1. synchronized + HashMap

  • 单线程安全，依赖锁，线程阻塞严重。
  • 适用于低并发环境，在高并发下锁竞争激烈。

2. ConcurrentHashMap + get+put

  • get -> 判断有无 -> put（需要显式处理并发问题）
  • 存在 竞态条件问题，需要再做 computeIfAbsent 或加锁，性能一般。

3. ConcurrentHashMap + merge()

  • 是线程安全的原子操作，封装了 get + put + update 的过程。
  • 没有显式加锁，性能最佳，最适合高并发统计场景。
map.merge(key, 1L, Long::sum)

意思是：如果 key 存在就自增，否则初始化为 1。
